如何正确地提设计建议

一份三步走的标准流程：先把代码拉到本地并挂载给 AI，再让它带着真实代码来评审你的方案。避免"没看过代码的建议"。

基线版本 V1.0.0 更新 2026-08-06 阅读约 4 分钟
为什么需要这套流程

脱离代码的设计建议，只能换来一句"听起来还行"

设计建议的价值 ＝ 方案本身 × 上下文准确度。如果评审者（无论是同事还是模型）没看过 agent-platform 的真实实现，它只会顺着你的描述附和，给出一份和现有架构冲突、却看起来很合理的结论。

这份 SOP 只解决一件事：让评审在看你的方案之前，先看过同一份代码。三步，五分钟。

STEP 01

按 tag 拉代码

统一使用 V1.0.0，保证所有人讨论的是同一份基线。

STEP 02

挂载本地目录

把 clone 出来的仓库根目录设为 AI 项目的 Source folder。

STEP 03

先读代码再评方案

提示词必须包含：先读代码 · 我的方案 · 要解决的问题。

标准流程

三个步骤，按顺序执行

每一步都有一个可验证的产出，做完再进入下一步。

1

把指定版本的代码拉到本地

目标产出：本地有一个处于 V1.0.0 的 agent-platform 仓库，并且你知道它的绝对路径。

Terminal
git clone -b V1.0.0 https://gitlab.bj.sensetime.com/sensespring-link/aigc/agent-platform.git
  • -b V1.0.0 不能省。不加分支/tag 会默认拉到 main，你和评审看的就不是同一份代码，讨论出的冲突点大概率是假的。
  • 记住绝对路径。示例中是 /Users/<你的用户名>/Downloads/agent-platform，第 2 步要用。
  • 已经 clone 过？执行 git fetch --all --tags && git checkout V1.0.0 切到同一基线即可，不必重新克隆。
不要用网页端下载的 ZIP。ZIP 包丢失 git 信息，既无法确认版本，也没法用 git log / git blame 佐证结论。
2

把本地仓库挂载成 AI 项目

目标产出：AI 工具能直接读到磁盘上的这份源码，而不是只读你贴进对话框的片段。

  • Source folder 必须是仓库根目录——就是含有 .git 的那一层（…/Downloads/agent-platform）。选成父目录 Downloads 会把无关文件一起喂进去，选成某个子目录则会漏掉关键实现。鼠标悬停可核对完整路径。
  • Project name 带上版本，例如 agent-platform-V1.0.0。一个版本一个 project，不要在同一个 project 里混入多份源码。
  • 如果你用的是 Claude Code、Cursor 等工具，等价动作是：在仓库根目录下启动，或把该目录加入工作区。
3

先让它读代码，再让它评你的方案

目标产出：一份引用了真实文件/模块名的评审意见，而不是泛泛而谈的"建议"。

  • 先验货再提问。输入框上方应显示 agent-platform · Local · V1.0.0。没有这一条，说明代码没挂上，回到第 2 步——此时问出来的任何结论都不作数。
  • 提示词必须包含三要素：先读代码、我的方案是什么、这个方案要解决什么问题。少了第三项，模型只会顺着你的方案夸。
提示词模板
请先阅读当前目录中 agent-platform 项目的代码，
然后分析我的这个设计方案是否合理？

【要解决的问题】
（现在哪里痛、影响谁、有没有可量化的现象）

【方案概述】
（做什么改动，分几步，关键取舍是什么）

【我认为会涉及的模块 / 文件】
（列出你的猜测，让模型来纠正）

【我不确定的点】
（明确写出你想被挑战的地方）

请重点回答：
1. 这个方案与现有实现有哪些冲突或重复？请引用具体文件和类名。
2. 有没有改动更小、能达到同样效果的替代方案？
3. 如果按此方案实施，风险最高的三个点是什么？
怎么判断它真读了代码：结论里应该出现具体的文件路径、类名、函数名。如果通篇只有"建议引入缓存层""可以考虑解耦"这类话术，说明它在凭空推测，追问一句"请给出对应的文件路径和代码片段"。
对照

同一个建议，两种写法

左边收到的回复通常是"听起来不错"，右边才能收到可执行的意见。

✗ 无效提法
✓ 有效提法
上下文直接在对话框里描述方案，不挂代码。
上下文先挂载 V1.0.0 源码，并在提示词里要求"先阅读代码"。
问题定义"我觉得任务调度应该改成事件驱动。"
问题定义"任务并发超过 N 时排队延迟明显上升，我想用事件驱动替换当前轮询，请判断是否成立。"
版本各看各的分支，"我这边不是这样的"。
版本所有讨论统一标注基线 V1.0.0。
提问方式"帮我把这个方案补充完整。"
提问方式"请指出方案与现有实现的冲突点，并给出改动更小的替代方案。"
产出一段聊天记录截图。
产出一页纪要：问题 → 方案 → 冲突点 → 替代方案 → 风险，附在 MR 描述或评审群里。

常见问题

大家最常问的四个

一定要用截图里这个工具吗？

不。任何能读取本地目录的 AI 编码工具都可以（Claude Code、Cursor、其他 IDE 插件等）。这份 SOP 约束的是流程本身——挂载真实代码 + 先读后评，不是某个具体产品。

仓库这么大，模型读得完吗？

不需要读完。在提示词里指明入口："重点看 xxx 模块及其调用方"。给出范围比让它自由发挥更准，也更省时间。

模型说我的方案不合理，就一定不做了吗？

不是。它的价值在于快速暴露你没意识到的冲突点和已有实现，最终判断仍由你和评审人做。把分歧点原样带到评审里，比私下纠结更有效。

拿到结论之后呢？

整理成一页纪要：问题 → 方案 → 与现有实现的冲突 → 替代方案 → 风险点，贴到 MR 描述或评审群。结论要能被别人复现：注明基线版本和你用的提示词。
