核心理念与六条铁律

AI 原生 ≠ 让 AI 替你干活,而是重构「谁定义、谁执行、谁负责」的分工。

传统模式下,人是执行主体,工具补全是辅助;AI 原生模式下,人是意图、约束与质量的主体,AI 是高吞吐的执行主体。开发者的核心能力从「编码快」转向把问题定义清楚、把约束表达清楚、把结果验证清楚。下面六条是所有环节都适用的底线。

🎯① 意图先行,规格即代码

先写清楚「要什么、不要什么、边界在哪」,再让 AI 实现。模糊的需求只会得到模糊且自信的代码。

🧩② 小步、可逆、可验证

每次只推进一个能独立验证的小单元;不可逆/对外动作(发布、删库、改线上)必须人工确认。

🔍③ 证据先于结论

「跑通了」「修好了」必须附运行输出。AI 说通过 ≠ 真通过,人也一样——先看证据再下判断。

🧠④ 上下文工程是第一生产力

给对上下文(规范、设计文档、Skill、记忆)比换更强的模型更有效。喂垃圾进、出垃圾出。

🤝⑤ 人对最终结果负责

AI 产出可以被质疑、被推翻。署名上线的人 = 责任人,不能用「AI 写的」当免责。

⏱️⑥ 设止损线

给 AI 任务设时间/失败次数上限(如 1 小时或连续 3 次失败即停),避免在死路上无限烧 token。

🧭 一句话原则
AI 显著降低了局部实现成本,但不会消灭工程成本;成本会转移到上下文、验证、评审、安全与维护。SOP 的重心因此前移到定义、约束、验证和治理。
★

背景: 编码 Agent 的价值与边界

编码 Agent 的主要价值,不只是「编码更快」,而是能降低需求澄清、上下文检索、设计草拟、测试补齐和重复性修改的成本。它能放大研发效率,但放大效果取决于驾驭 Agent 的人在系统设计、技术掌握、业务 know how 的知识沉淀、需求稳定性、上下文可获得性、验证体系和团队使用方式。

🗣️需求确认大幅提效

可用快速原型、可运行 demo 或交互稿对齐需求,减少抽象讨论带来的偏差。对外展示时必须标注 demo 的验证范围,避免把探索性原型误认为可交付产品。

📥规模化获取显式上下文

Agent 能从代码、文档、提交记录和测试里快速提取上下文,降低交接损耗。但它不会天然理解隐式业务知识;关键约定必须沉淀为文档、类型、测试或运行证据。

📐存量梳理 + 风险分层覆盖

Agent 适合梳理存量代码、补齐 spec、厘清模块职责。覆盖要求按风险分层:核心链路、权限、资金、数据安全、复杂状态机必须重点覆盖;低风险改动可轻量化。

⚡突破部分协作瓶颈

在需求相对清晰、模块边界明确、验证体系健全的项目里,Agent 可以减少「加人带来的沟通成本」。不承诺固定倍数;每个项目应以交付周期、缺陷率和返工率来评估收益。

🧱 关键转变
Agent 可以把部分上下文传递、需求澄清和重复实现转化为可规模化操作,但前提是上下文可检索、接口可描述、验证可执行。真正的收益来自减少低价值传话,而不是取消必要的人类判断。

对组织协作的影响

🎯重心转向价值确认

实现成本下降后,瓶颈更容易前移到「做对的事」。团队需要把更多精力放在业务价值、用户路径、风险边界和验收口径上。

🔗减少低价值同步

能由文档、代码、测试和 Agent 自动汇总解决的问题,不再依赖反复开会传话。高风险决策、资源冲突和跨团队承诺仍需明确责任人。

💡 给团队的启示
本 SOP 的核心不是鼓励「少管代码」,而是把人的注意力从重复实现转移到目标定义、风险识别、质量裁决和上线责任。

减少不必要的人为摩擦,保留必要的人类判断

AI Native 的目标不是让人从流程里消失,而是减少低价值的人肉转述、等待和重复解释。需求取舍、架构责任、安全合规、上线审批、异常处理等关键节点必须保留明确的人类责任人。

🧠 协作原则
能被文档化、版本化、自动验证的上下文,应尽量交给 Agent 和工具链处理;涉及权限、隐私、客户承诺、组织边界和不可逆后果的事项,必须走明确的审批和责任链。

更合理的组织目标是减少以下噪音,而不是取消治理:

🔒权限不透明

把数据/代码访问等级、申请路径和脱敏要求写清楚,减少无效等待。

⏳排期黑箱

用清晰的优先级、依赖关系和交付标准替代反复口头同步。

🙅责任不清

每个设计、实现、评审、上线动作都有责任人和证据链。

📈重复解释

将常见问题、运行命令、业务约束沉淀到团队共享上下文。

1

框架与模块设计

先对齐意图与边界,再让 AI 填充实现;接口与契约是 AI 协作的「公共语言」。

1.1 设计先于编码:用 AI 做发散,用人做收敛

  • 需求澄清(Brainstorm):动手前先和 AI 过一轮——目标、用户、约束、非目标、失败模式、可选方案与取舍。让 AI 主动反问、列出不确定点,而不是直接给方案。
  • 设计文档作为需求与决策事实源:由人给出初始推动的想法,再由 AI 起草设计文档(目标 / 模块边界 / 接口 / 数据流 / 风险),人 review 后定稿。需求、取舍和边界以设计文档为准;代码、测试和线上行为是实现事实源,变更时必须同步更新。
  • 多方案并行评审:对关键设计让 AI 产出 2–3 个独立方案(如「最小可用优先 / 风险优先 / 扩展性优先」),再由人择优并嫁接各自亮点。
🔁 实操经验:设计文档先反复交叉评审到收敛,再动手
正式开发前先写设计文档,然后让 Claude Code 和 Codex 分别多轮 review,把发现的问题逐条修订,直到两个 Coding Agent 都认为设计文档不再有任何问题为止。人也必须参与这一轮:把自己的关注点、以及觉得不对或有风险的地方明确告诉 Agent,让它按你的思路去 review 或修改,而不是被动接受 AI 的判断。设计阶段多花的时间,远低于在错误架构上返工的成本。

1.2 设计分层门槛

任务类型最低设计要求必须评审
低风险小改一句话目标 + 验收标准 + 影响文件代码 owner 或责任人自查 + 异构 AI 交叉评审
普通功能目标 / 非目标 / 接口 / 数据流 / 测试计划模块 owner review + 异构 AI 交叉评审
高风险改动方案对比 / 兼容性 / 回滚方案 / 权限与数据影响 / 发布计划模块 owner + 相关方 + 异构 AI 交叉评审

1.3 模块设计原则(对 AI 协作友好)

接口先行

先定义清晰的接口/契约/类型,AI 在明确契约下实现质量显著更高,也便于替换实现。

边界清晰、低耦合

模块可独立理解、独立测试。清晰的边界 = 可拆成多个并行子任务交给多 Agent。

可独立验证

每个单元都有「怎么算对」的判定标准,这是后续自动化验证与并行化的前提。

显式优于隐式

命名、目录约定、错误处理写清楚;AI 主要依赖可见上下文,隐式约定必须转成文档、类型、测试或示例。

💡 实践提示
把项目级约定沉淀进 CLAUDE.md / AGENTS.md(技术栈、目录结构、命名、禁忌、构建与测试命令)。这是给所有 AI 协作的「项目宪法」,一次写好长期复用。
⛔ 反模式
跳过设计直接「帮我实现这个功能」→ AI 在错误的架构上高速产出大量代码,返工成本远高于省下的设计时间。越大的任务,设计阶段的杠杆越高。
2

Coding 编码

测试驱动 + 小步提交 + 风格对齐;复杂任务先出计划再动手。

2.1 标准节奏

STEP 1
明确单元目标与验收标准
STEP 2
先写/补测试(红)
STEP 3
AI 实现至测试通过(绿)
STEP 4
重构 + 自查 + 小步提交

2.2 关键做法

  • 复杂任务先进 Plan 模式:让 AI 先给出实现计划(改哪些文件、什么顺序、风险点),人确认后再执行,避免「一把梭」跑偏。
  • 小 diff、勤提交:每个 commit/PR 对应一个可描述、可回滚的改动;便于 review 与定位回归。
  • 风格对齐既有代码:让新代码在命名、注释密度、惯用法上与周边一致,而不是 AI 自带的风格。
  • 独立子任务并行化:互不依赖、无共享状态的多个任务,可派发多个子 Agent 并行;有依赖则串行,避免并行制造冲突。
  • 人工守住高危操作:涉及发布、数据删除、改线上配置、对外发送等不可逆动作,AI 暂停、人确认。

2.3 并行 Agent 操作约束

  • ✓先切任务边界:每个 Agent 只负责一个可验证子目标,明确可改文件范围和不可改区域。
  • ✓隔离工作区:并行实现优先使用独立 branch/worktree,避免多个 Agent 同时改同一批文件。
  • ✓集中合并:由人或主 Agent 统一合并,逐个跑测试和验证;不要把多个 Agent 的 diff 一次性混合提交。
  • ✓保留证据链:每个子任务交付时必须说明改动、测试命令、结果、已知风险和未覆盖范围。
✅ 推荐
把「怎么构建、怎么跑测试、怎么本地启动」写进项目文档并让 AI 自己执行验证——它能闭环自查,你只看结论与证据。
⛔ 避免
一个 prompt 让 AI 写完整个功能后直接采纳。大块未经分段验证的代码,是回归与隐性 bug 的高发区。
3

Code Review

AI 先做一遍机器评审,人聚焦判断与上下文;对 AI 的反馈要核实,不要盲从。

3.1 双层评审:机器 + 人

层谁来做关注点
第一层
机器评审		AI(自动化 review / 安全扫描 / 静态检查)常见 bug、空指针、边界、未处理错误、明显安全问题、风格一致性、与计划的偏离
第二层
人工评审		评审人是否真正解决了问题、架构是否合理、可维护性、业务正确性、AI 看不到的上下文与权衡

3.2 评审清单

  • ✓改动是否对齐设计文档/计划?有无偷偷扩大范围(scope creep)?
  • ✓是否有对应测试且确实覆盖了改动与边界,而非凑数?
  • ✓错误处理、边界、并发、空值是否考虑充分?
  • ✓有无看似合理但实则错误的实现(AI 幻觉重灾区)?对可疑点做对抗式核实。
  • ✓是否引入未声明的依赖、隐藏的副作用、被静默吞掉的异常?
  • ✓是否影响权限、数据范围、日志脱敏、外部 API、配置和部署脚本?
  • ✓新增依赖是否有许可证、维护状态、漏洞和供应链风险评估?
  • ✓命名/风格是否与既有代码一致,是否可维护?

3.3 交叉评审:换一个 AI 来挑刺(强烈推荐)

🔀 异构交叉评审
实践发现:AI 很难 review 出自己写的设计/方案的问题——它会复用产出时的同一套假设,对自己的盲点免疫。换一个 AI(如 Claude Code 写、Codex 评,或反之),常能暴露实现方忽略的正确性、边界或安全问题。让一方实现、另一方专门「挑刺」,是低成本、高收益的质量手段。
角色分工要点
实现方
(如 Claude Code)		设计 + 编码 + 自测产出方案与代码,先完成自查
评审方
(如 Codex)		对抗式 review以「假设实现方错了」为前提找漏洞,重点盯 P0:正确性、边界、安全、架构缺陷
人裁决收口核实交叉评审暴露的问题是否成立,决定采纳/反驳
  • 关键节点必交叉:设计方案、核心模块、高风险改动,定稿前过一遍「换一个 AI」。
  • 双向都做:谁写的不重要,重要的是评审方与实现方不是同一个模型,避免共享盲点。
  • P0 优先:让评审方先报「会导致严重后果」的问题,再谈风格与优化。

3.4 接收评审意见(对 AI 也对人)

🧪 技术严谨,而非表演式同意
收到「建议这样改」时——先核实:这条意见技术上成立吗?有没有反例?成立才改,不成立要讲清为什么。盲目照改和盲目拒绝同样有害。

对抗式验证小技巧:对一个可疑结论,派几个「专门挑刺」的视角去反驳它(正确性 / 安全 / 能否复现);多数都驳不倒,才算站得住。

4

Test 测试

测试是 AI 时代的「安全绳」——它把「AI 说对了」变成「机器证明对了」。

4.1 测试驱动开发(TDD)红-绿-重构

RED
先写会失败的测试,锁定期望行为
GREEN
AI 写最小实现让测试通过
REFACTOR
测试护航下重构,保持绿

测试先行的额外价值:它把模糊需求逼成可执行的规格。一旦测试写清楚,AI 实现的命中率显著提升,也天然防止「实现跑偏却自称完成」。

4.2 让 AI 增强测试,而不是替代判断

  • 让 AI 主动列边界与异常用例(空值、超长、并发、越权、网络失败),人补业务关键路径。
  • 覆盖率是参考不是目标;关注关键路径与高风险分支是否真被测到。
  • 警惕「为通过而写的测试」——断言空泛、mock 掉了真正逻辑。Review 测试本身,和 review 代码一样重要。

4.3 测试覆盖分层

风险等级示例最低测试要求
低文案、样式、非核心展示逻辑可用人工验证或快照/视觉检查,记录验证证据
中普通业务功能、接口适配、状态变更单测或集成测试覆盖主路径 + 关键边界
高权限、计费、资金、隐私数据、迁移、并发、删除操作单测 + 集成/端到端测试 + 失败路径 + 回归用例;必要时加人工 checklist
⛔ 危险信号
AI 为了让测试变绿,去改测试迁就实现而非修实现。任何「放宽断言/删用例」的改动都要人确认意图。
5

Verification 验证收口

单测过 ≠ 真的好用。在「真实环境/真实路径」上验证,并以证据收口。

5.1 测试 vs 验证

Test 测试Verification 验证
问的问题代码逻辑对不对?它在真实场景里真的解决了问题吗?
层面单元 / 集成端到端 / 真实运行 / 用户视角
方式自动化断言跑起来、看输出、对照预期行为

5.2 验证铁律

  • ✓证据先于断言:宣称「完成/修好/通过」前,跑命令、贴输出,确认无误再说。
  • ✓在真实应用里验证,不只跑单测——真正启动应用、走一遍用户路径。
  • ✓验证「真的生效了」:热更新/配置变更后,确认实际加载的就是新版本(踩过坑:挂载路径/版本不匹配导致静默无效)。
  • ✓失败如实上报:测试挂了就贴输出说挂了;跳过了就说跳过;不粉饰。
  • ✓可行性门槛 + 止损:动手前先判断这条路是否可行;触发止损线(超时/连续失败)即停并复盘。

5.3 发布与回滚收口

  • 发布前:确认迁移脚本、配置变更、feature flag、依赖升级和外部 API 影响;高风险改动必须有回滚方案。
  • 发布中:优先灰度、小流量或开关控制;不可逆动作必须人工二次确认。
  • 发布后:检查核心指标、错误日志、告警、用户路径和版本命中情况;异常时按回滚方案处理,而不是让 AI 临场猜修。
🔒 收口标准(Definition of Done)
① 设计被实现且未越界 · ② 测试按风险等级覆盖且真实通过 · ③ 人工评审通过 · ④ 安全/权限/依赖影响已检查 · ⑤ 真实环境验证有证据 · ⑥ 发布、灰度、回滚和监控计划明确 · ⑦ 责任人确认署名上线。七项齐全才算「完成」。
6

安全、权限与治理

AI 可以提升吞吐,但不能绕过数据边界、权限边界和上线责任。

6.1 数据与上下文分级

级别示例AI 使用规则
公开/内部公开公开文档、通用技术资料、无敏代码片段可直接使用,仍需核实来源和版本

6.2 高风险操作门禁

  • ✓密钥与凭证:不得让 AI 生成、复制、提交或暴露真实密钥;发现泄露立即轮换。
  • ✓生产数据:查询、导出、删除、批量修复必须有工单/审批/备份/回滚路径。
  • ✓外部发送:邮件、短信、推送、客户通知、公开发布必须人工确认最终内容和收件范围。
  • ✓权限变更:账号、角色、ACL、网络策略和安全组变更必须由责任人 review。
  • ✓依赖引入:新增三方包、镜像、脚本和 MCP/插件必须确认来源、权限和维护状态。
⛔ 底线
不能因为「AI 能处理更多上下文」就扩大数据暴露面。上下文越多,越要做最小权限、脱敏、审计和可回滚设计。

7.2 工具链沉淀

📜项目宪法

CLAUDE.md/AGENTS.md:技术栈、结构、命名、禁忌、构建与测试命令、安全边界——所有 AI 协作的统一前提。

🧠跨会话记忆

把踩过的坑、团队约定、长期上下文沉淀为可复用记忆;写入前先确认不包含密钥、客户数据和临时误判。

🛠️技能/SOP 化

把高频流程(评审、调试、发布前检查)固化成可调用的标准流程,降低发挥波动。

⛓️多 Agent 编排

独立任务并行(fan-out)、关键结论对抗式核验、再汇总收口;复杂工作拆成可验证子任务,并隔离分支/工作区。

✅ 实操经验:让好经验跨项目复用
把你认为通用的编程规范和需要持久记忆的信息集中写进一个独立文件(例如 /Users/user1/Desktop/keynotes.md),再在每个项目的 CLAUDE.md / AGENTS.md 里加一句引用,比如:『请阅读并在执行任务过程中遵守 /Users/user1/Desktop/keynotes.md』。这样同一套经验和约定就能自动应用到所有项目,不必在每个仓库里重复维护;更新一处,处处生效。
💡 团队层面
个人的好用 prompt 与流程要沉淀为团队共享资产(规范文件 / 技能库 / 评审清单 / 安全门禁),让 AI 原生能力从「个人手艺」变成「组织能力」。
