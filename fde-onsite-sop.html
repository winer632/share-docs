1背景与目标

随着交付项目增多，现场 FDE（Forward Deployed Engineer）与后场研发团队需要一套明确的协作 SOP，以厘清职责边界、统一工作流程、保障交付质量。本 SOP 以本次 CSTCB 项目的实际合作模式为基础形成初版，后续随项目实践持续修订。

本 SOP 的目标：

  • 明确前场（FDE）与后场（研发）的职责边界与代码修改权限；
  • 建立以 case 列表为核心的统一工作与验收机制；
  • 规范项目仓库、SensePedia 主仓库的分支与特性回流流程；
  • 为疑难问题定位、误判防范提供标准处理路径。

2总体协作模式

核心原则：研发团队负责基础设施和标品，FDE 专注于业务层（当前阶段业务层主要指 MCP Server 与 skills）。

  • FDE 在客户现场接收需求，快速开发和调试 MCP Server 与 skills，并直接与客户确认效果；
  • 研发负责 SensePedia 标品机制能力建设（离线 skill 支持、MCP Server 调用机制、Agent 响应速度等），并对基础架构类问题提供标准修复流程与远程支持；
  • 项目中沉淀的通用特性，经评审后回流 SensePedia 标品主分支，形成"项目反哺标品"的循环。

说明：模式起步阶段职责界限不会一次性完全清晰，边界的逐步明确本身就是本 SOP 的建设方向之一。

3角色与职责分工

FDE 角色定位

FDE 当前定位不是纯前场技术角色，而是售前 + 前场技术的复合角色（分别对应 3.1、3.2 两节），通常一名 FDE 同时负责 1–2 个项目。该负荷约束是第 9 节支援机制议题的前提。

3.1 前场技术角色：前后场分工

现场 FDE 前场

  • 接收客户需求，快速开发和调试 MCP Server 与 skills；
  • 负责 prompt 层调整、测试，并与客户确认效果；
  • 维护项目 case 列表（唯一需求 / 问题入口）；
  • 支持胶水层服务（基于 Pedia 基础能力封装客户特殊定制型服务，例如定时发送分析报告）；
  • 非基础架构类代码修改 + 提供测试 case；
  • 疑难问题的现场验证定位与二次确认。

研发团队 后场

  • SensePedia 机制开发：离线 skill 支持、MCP Server 调用机制、Agent 响应速度等；
  • 基础架构类代码的标准修复流程与重构；
  • FDE 代码修改的复核；重构后以研发代码为准；
  • 疑难问题快速远程响应、内部复现定位；
  • 项目初期为 FDE 提供 prompt 调优远程支持；
  • 与产品经理共同评审特性回流标品主分支。

3.2 售前角色：对内传递客户需求

FDE 作为售前角色的核心职责是对内传递客户需求，产出物为「售前需求」，作为后续产品需求的输入。

售前需求的编写边界

售前需求只描述用户需求，不带产品方案或技术方案设计：

  • 应包含：客户是谁、业务场景、要解决的问题与痛点、期望达到的效果、优先级；
  • 不应包含：产品功能方案、技术实现方案、架构或接口设计——这些在需求转化阶段由产品与研发侧补齐。

需求转化关系：

产品需求 = 售前需求 + 现有产品知识 + 新增产品功能方案设计
  • 售前需求：由 FDE 提供，只描述用户需求，是客户诉求的忠实记录；
  • 现有产品知识：结合标品已有能力，识别哪些需求现有功能已可满足；
  • 新增产品功能方案设计：对现有能力无法覆盖的部分，由产品与研发侧设计新增功能方案。

与第 5 节的关系：项目交付过程中的效果问题与需求变化，仍统一进入 case 列表；售前需求主要承载新项目、新功能方向的客户诉求传递。

4仓库与分支策略

仓库内容策略
项目专属仓库 FDE 开发的 MCP Server、skills（业务层交付物） 每个项目建立专门的 GitLab 仓库，由 FDE 主导维护
SensePedia 标品仓库 标品机制与基础设施代码 独立 GitLab 仓库，每个项目拉独立分支开发，由研发主导维护

特性回流流程

项目开发：项目特性在 SensePedia 项目分支 + 项目专属仓库中实现并交付
↓
积累评审：若干项目完成后，产品经理与研发共同评审各项目特性
↓
回流主分支：确定有通用价值的特性 merge 到 SensePedia 主分支，成为标品能力
特殊分支模式的约束

短期内在标品不具备可插拔条件时，"项目特殊分支"是最快速的交付方案，但该模式不能持续过多项目，否则代码仓库会非常混乱。中长期必须向第 8 节的可插拔模块化方向演进。

5以 case 列表为核心的工作流程

case 列表是前后场共同的工作核心和唯一事实来源：

  1. 统一入口：所有效果问题或客户需求变化，统一首先更新到 case 列表，由 FDE 负责维护；
  2. 转化为验收标准：case 列表最终转化为项目验收标准，前后场均以此为工作核心；
  3. 驱动排查与验证：问题定位、修复验证、客户确认均围绕对应 case 进行，避免口头传递导致的信息漂移。

6问题分层处理规则

6.1 prompt 层问题

  • 可通过 prompt 调整解决的问题，由 FDE 负责调整和测试，并与客户确认效果；
  • 项目初期产研提供远程支持，协助 FDE 熟悉 prompt 在当前项目中的特点。

6.2 代码类问题（分两大类）

第一类：基础架构类 —— FDE 禁止修改

以下范围的代码问题必须走产研标准修复流程：

  • 核心调度算法
  • Agent 状态机
  • 中间件 / 数据库连接
  • 模型封装
  • RAG 检索
  • 核心交互框架
第二类：其他代码问题 / 功能调整 —— FDE 可修改
  • 由 FDE 修改并提供测试 case，产研复核；
  • 如果产研对调整进行重构，则以产研重构代码为准，FDE 测试现场效果；
  • 重构后现场再出现问题，按照新问题流程处理（重新进入 case 列表）。

6.3 疑难问题定位

快速响应：产研对疑难问题的原因分析提供快速远程响应
↓
路径 A（具备现场验证条件）：优先指导 FDE 现场验证定位
或
路径 B（不具备现场条件）：产研与测试内部复现定位，确定问题点后由 FDE 现场二次确认

7磨合期预期与误判防范

模式起步阶段的合理预期：初期研发侧任务会偏重，因为会有不少前场误判的问题落到后端排查。从长期看，这属于产品与协作模式成长的必经过程。

典型误判案例（供排查参考）

调试模板 skill 时，监控 prompt 发现输出总是提到"应使用 memory 进行参考"，整个调用流程与 skill 要求几乎完全不一致，现象上极易被判断为基座问题。实际原因是：MCP Server 更新重启，恰好撞上平台定时检活机制触发，平台判定 MCP 已挂；而 skill 又要求必须使用该 MCP，LLM 认为此路不通，转而查找 memory 参考。几分钟后检活再次触发即自行恢复。

启示：skill 效果异常时，先确认 MCP Server / 检活等基础设施状态与时间线，再定位 skill 与 prompt 层，避免被表面现象误导。

8代码演进方向：可插拔模块化与标准配置化

  • 标品代码长远应当按照可插拔模块化 + 标准配置化的模式演进，使 FDE 可参与调整的代码范围逐渐增加并趋于标准；
  • 短期不具备条件时以特殊分支方式过渡（受第 4 节约束限制）；
  • 落地方案由研发侧调研后补充到本文档（见第 9 节开放议题）。

10文档维护方式

  • 本文档存放于项目 GitLab 仓库，作为 FDE 工作 SOP 的唯一权威版本；
  • 修订通过 GitLab 提交进行，重大变更（职责边界、禁改清单、流程调整）需前后场双方确认；
  • 随项目实践发现的边界模糊点，先记入第 9 节开放议题，讨论定稿后正式并入相应章节。
